# 下一餐推荐业务规则

> 本文件定义下一餐推荐的核心业务规则，包括硬约束、候选筛选、排序、场景路由、输出与降级原则。


## 1. 推荐总原则

下一餐推荐分为两个阶段：

### 硬过滤

硬约束优先于所有排序因素。

以下候选直接排除：
- 与用户明确过敏或严格忌口冲突；
- 与用户当前已选择的就餐场景冲突；
- 必须依赖当前无法验证的真实世界事实才能成立。

硬约束不能通过“更符合热量”“更符合偏好”“距离更近”等排序优势被覆盖。

### 候选排序

通过硬过滤后，按以下因素综合选择：

1. 当餐营养匹配；
2. 用户偏好；
3. 当前现实条件；
4. 时间 / 距离；
5. 数据可信度。

默认返回 1 个明确主推荐，必要时提供 1–2 个备选；不要一次性返回大量候选，让用户重新承担选择成本。

## 2. 硬约束

推荐前后必须满足：

- 过敏 / 严格忌口是硬约束，任何候选都必须排除；
- 热量与蛋白质预算来自系统或 Tool，不由 LLM 自行修改或重新计算；
- 不编造餐厅、菜单、位置或其他实时外部数据；
- 无法核验具体菜单时，进入“店型降级”而不是编造菜单；
- 营养和热量无法精确获得时，明确说明为估算；
- 不提供疾病诊断、药物调整或治疗方案；
- 触发产品安全风险时，先明确展示风险提示，再按产品定义继续后续流程；
- 涉及写入饮食记录时，只能生成确认提案，由用户确认后入账。

## 3. 安全规则

安全规则由确定性程序判断，LLM 不得修改阈值、不得隐藏或弱化风险。

如果 `targets.safety` 存在，必须如实转述其中的 `warning`。常见风险包括：

- 目标 BMI 低于 18.5；
- 理论目标减重速度超过 1 kg/周

命中风险时，产品策略是“可给方案，但必须带风险提示”，而不是拒绝服务。

## 4. 餐次与预算规则

- 餐次归一为：早餐、午餐、晚餐、其他摄入。
- 用户没有明确餐次时，按产品日期口径（Asia/Shanghai）的当前时间推断：早于 10:00 为早餐，早于 16:00 为午餐，否则为晚餐。
- 本餐预算由 `get_meal_budget` / `mealTargets` 计算，不要自己估算。
- 正餐预算会为后续餐次预留；其他摄入不分配独立正餐预算，剩余热量应保留给后续正餐。
- 用户说“明天”时，先计算明天对应的餐次预算，不要拿今天预算替代。

## 5. 场景路由

### 5.1 在家 DIY

适用条件：用户明确在家吃，或提供现有食材，或表达想做一顿。

必须获得：

- 现有食材；
- 必要时的烹饪时间和厨具；
- 本餐预算；
- 偏好 / 忌口。

输出应包含：

- 菜名；
- 主要食材及克数；
- 简要制作步骤；
- 预计耗时；
- 单一近似热量；
- 推荐理由和与预算的关系。

营养值由 DIY 工具按本地数据库实算；查不到可靠营养的食材，不要强行生成精确数值。

### 5.2 附近餐厅

适用条件：用户明确到店吃，或提供位置 / 商圈，或表达“附近有什么”。

必须获得：

- 可用的位置或商圈；
- 本餐预算；
- 偏好 / 忌口；
- 来自真实餐厅查询 Tool 的候选；
- 在可用情况下获取可核验的菜品信息。

输出应包含：

- 餐厅名称；
- 推荐菜品或适合的店型；
- 点餐调整建议；
- 推荐依据；
- 数据来源与可信度。

餐厅候选必须来自真实 Tool 结果。

只有获得可核验菜品信息时，才能推荐具体菜品；
无法核验时，降级为店型和点餐策略推荐，并明确说明信息限制。

具体餐厅数据源及字段可信边界见：
`references/amap-api.md`

### 5.3 场景未明确

只有当缺少的信息会明显改变推荐结果时，才向用户追问。

不要为了“收集完整信息”而追问系统已经知道的信息，例如已经知道餐次、忌口、位置时，不要重复询问。

## 6. 候选筛选

对候选方案逐项检查：

- 不违反用户明确过敏 / 忌口；
- 推荐目标值，而不是绝对禁止超过的硬上限；
- 符合当前就餐场景；
- 使用的外部信息具有可靠来源；
- 推荐在现实条件下可以执行。

优先级：真实菜单 > 高德特色菜 > 店型降级；在同等来源可信度下，再按营养匹配、偏好、距离和营业状态排序。

## 7. 数据可信度

推荐使用外部数据时，应根据数据来源和可验证程度决定能够做出的结论。

基本原则：

| 数据类型 | 推荐时的使用方式 |
|---|---|
| 结构化营养数据 | 可作为营养计算依据 |
| 可核验餐厅数据 | 可用于确认真实餐厅 |
| 可核验菜单 / 菜品信息 | 可用于推荐具体菜品 |
| 信息有限的菜品候选 | 只能作为辅助参考，不视为完整实时菜单 |
| 无法核验的餐厅菜品信息 | 不作为具体菜品事实使用 |
| 店型降级 | 只提供店型和点餐策略，不编造具体菜单 |

具体数据源规则分别见：

- 营养数据：`references/nutrition-data.md`
- 高德餐厅数据：`references/amap-api.md`

## 8. 输出规则

最终回答应优先给 1 个主推荐，并说明：

- 推荐吃什么；
- 单一近似热量；
- 推荐理由；
- 与当前餐次预算的关系；
- 必要的执行建议。

如果需要备选，再给 1–2 个，不展开大量候选。

所有面向用户的估算数值只给单一值，不输出区间；必须同时保留误差来源或“估算 / 待确认”提示。

## 9. 失败与降级

| 情况 | 处理 |
|---|---|
| 没有位置 | 引导用户提供城市、商圈或允许定位 |
|  餐厅搜索 Tool 失败 | 不编造餐厅，降级为店型 / 点餐策略或引导用户补充信息 |
| 菜单不可核验 | 改为店型推荐，并明确信息限制 |
| 营养查不到 | 明确说查不到，不做无依据的精确承诺 |
| 工具失败 | 更换可行方案或引导用户补充信息，不空转重试 |

原则：宁可降低推荐精度，也不伪造真实世界数据。
