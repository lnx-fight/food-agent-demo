# 下一餐推荐

## 目标

结合用户当前饮食状态、减脂目标、饮食偏好、忌口以及现实就餐条件，
帮助用户完成“下一餐吃什么”的决策，并给出可以直接执行的建议。

## 核心流程

1. 理解用户当前请求，确定本次需要规划的餐次以及用户已经明确表达的要求。

2. 获取完成当前推荐所必需的信息，优先使用：
   - 当前对话；
   - 用户状态；
   - 已有 Memory；
   - Tool 返回结果。

   不要求用户重复提供系统已经知道的信息。

3. 判断当前就餐场景。

4. 根据场景进入对应推荐流程：
   - 在家 DIY；
   - 附近餐厅 / 到店；
   - 场景未明确。

5. 根据当前约束对候选方案进行筛选和排序。

6. 返回一个明确、可执行的下一餐建议。

## 场景分流

### 1. 在家 DIY

满足以下任一情况时，可进入 DIY 流程：

- 用户明确说在家吃；
- 用户明确表示自己做饭；
- 用户提供了家中现有食材；
- 用户明确选择了 DIY 场景。

进入 DIY 流程后：

- 返回 `action.type=open_diy` 作为本次分流动作；
- 基于用户真实现有食材生成方案；
- 结合当前餐次预算、偏好和忌口；
- 必要时考虑烹饪时间、厨具等现实条件；
- 不要求用户提供系统已经知道的信息。

具体 Tool 的选择与调用顺序按 `references/tool-guide.md` 执行。

营养数据的查询、匹配和可信度判断按 `references/nutrition-data.md` 执行。

### 2. 附近餐厅 / 到店

满足以下任一情况时，可进入餐厅流程：

- 用户明确说附近吃；
- 用户明确说出去吃、到店或找餐厅；
- 用户提供了位置、商圈或明确选择了餐厅场景。

进入餐厅流程后：

- 返回 `action.type=open_restaurants` 作为本次分流动作；
- 使用真实位置或商圈作为推荐基础；
- 获取真实餐厅候选；
- 根据当前餐次预算、偏好和忌口生成推荐；

具体 Tool 的选择与调用顺序按 `references/tool-guide.md` 执行。

餐厅、菜单和高德数据的可信边界按 `references/amap-api.md` 执行。

### 3. 场景未明确

当用户只是表达：

- “中午吃什么？”
- “下一餐吃什么？”
- “帮我选一顿。”
- “我现在不知道吃什么。”

但没有明确表达：

- 在家 / 自己做 / 使用现有食材；
- 附近 / 出去吃 / 到店 / 餐厅；

则视为当前就餐场景未明确。

此时：

- 不替用户直接选择 DIY；
- 不替用户直接选择附近餐厅；
- 不提前进入具体推荐链路；
- 返回 `open_meal_choice`，让用户先选择“在家 DIY”或“附近餐厅”。

场景分流是进入具体推荐流程前的必要步骤。

### 场景分流动作映射

- 场景明确为在家 DIY → 返回 `action.type=open_diy`；
- 场景明确为附近餐厅 / 到店 / 外卖 → 返回 `action.type=open_restaurants`；
- 场景未明确 → 返回 `action.type=open_meal_choice`。

动作类型必须与已确定的场景一致，不得在场景明确时返回 `none` 或其他动作。

## 推荐决策

进入具体场景后，根据当前用户约束和候选结果完成推荐。

具体的：

- 硬约束；
- 候选筛选；
- 推荐排序；
- 营养匹配；
- 偏好使用；
- 数据可信度；
- 主推荐与备选数量；
- 失败和降级策略；

统一按 `references/recommendation-rules.md` 执行。

不要在本 Skill 中重新定义这些规则。

## 追问原则

只有缺少的信息会阻塞当前下一步执行，或会明显改变推荐结果时，才向用户追问。

优先追问当前最关键的一项信息，不为了“收集完整信息”一次性询问多个非必要问题。

已经存在于当前对话、用户状态、Memory 或 Tool 结果中的信息，不重复询问。

## 输出

最终应给出可以直接执行的下一餐建议。

## 完成标准

本 Skill 的一次任务仅在以下可观察结果全部成立时结束：

- Router 已将餐食场景确定为 `diy`、`restaurants` 或 `unknown`；
- 返回的 `routing.routerAction` 和最终 `action.type` 与该场景的动作映射一致；
- 返回非空的面向用户回答；
- `diy` 或 `restaurants` 场景已经给出可执行建议，或明确说明了继续执行所必需的唯一信息；
- `unknown` 场景只进入 `open_meal_choice`，让用户选择 DIY 或附近餐厅，不预先进入任一具体推荐链路。

不要以“已经开始查询”“可以帮你推荐”等中间状态作为完成。Router 入口回归由 `meal-choice-eval` 覆盖；多轮任务完成由 `task-trajectory-eval` 覆盖。

### DIY 场景

应尽量包含：

- 推荐餐食；
- 主要食材及份量；
- 简要制作方式；
- 预计耗时；
- 与当前餐次预算的关系。

### 附近餐厅场景

应尽量包含：

- 推荐餐厅或适合的店型；
- 推荐菜品或点餐策略；
- 推荐依据；
- 与当前餐次预算的关系；
- 必要的数据来源或信息限制说明。

具体推荐数量、估算表达和降级规则按 `references/recommendation-rules.md` 执行。

## Examples

### 示例 1：明确 DIY

用户：
“中午不知道吃什么，家里有鸡胸肉、番茄和鸡蛋。”

正确判断：

- 用户已经提供现有食材；
- 场景明确为 DIY；
- 返回 `action.type=open_diy`；
- 直接进入 DIY 推荐流程；
- 不再询问“你是在家吃还是出去吃”。

### 示例 2：明确附近餐厅

用户：
“我中午出去吃，帮我看看附近有什么合适的。”

正确判断：

- 场景明确为附近餐厅；
- 返回 `action.type=open_restaurants`；
- 使用已有位置，或在缺少必要位置时补充位置；
- 进入餐厅推荐流程。

### 示例 3：场景未明确

用户：
“中午吃什么？”

正确判断：

- 当前没有 DIY 或餐厅场景证据；
- 返回 `open_meal_choice`；
- 不直接生成 DIY 食谱；
- 不直接搜索附近餐厅。

### 示例 4：已有信息不要重复问

用户：
“还是帮我找附近吃的吧。”

当前上下文已经知道：

- 当前规划午餐；
- 用户不吃花生；
- 系统已有位置。

正确处理：

- 直接进入附近餐厅流程。

不要再次询问：

- “你要吃哪一餐？”
- “有什么忌口？”
- “你在哪里？”
