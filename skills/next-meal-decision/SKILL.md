# 餐食决策

## 作用

本 Skill 是模型完成“下一餐决策”的标准操作流程，用于稳定复杂情境理解、信息优先级、Tool 编排和输出边界。

它不负责热量与营养计算、日期计算、饮食记录写入或周计划刷新；这些结果必须来自确定性程序、受控 Tool 和用户确认。每次确认餐食记录后，当天未执行餐次及日终未来计划会由产品状态机自动刷新，不需要本 Skill 生成计划补丁。

## 适用场景

用户的目标是得到一顿现在可以执行的具体餐食：

例如：

- “中午吃什么？”
- “家里有鸡胸肉和番茄，晚饭怎么做？”
- “帮我看看附近有什么适合减脂的餐厅。”
- “今晚加班，晚饭吃什么好？”
- “中午吃多了，晚餐具体吃什么？”
- “今天起晚了没吃早餐，冰箱有剩菜且微波炉坏了，晚上可能吃爆米花，午餐怎么安排？”

按 [下一餐 Tool 编排](references/tool-guide.md) 执行；候选筛选与排序按 [推荐规则](references/recommendation-rules.md) 执行。需要营养或餐厅数据时，再分别读取对应 reference。

## 不进入本 Skill

- 首次生成固定自然周计划：交给确定性周计划功能；
- 每次记餐后的当日剩余餐次刷新、日终未来计划温和更新：由确定性计划状态机执行；
- 仅要求查看、锁定、结束当天或重新生成整个自然周：使用周计划功能；
- 记录已经吃过的餐食或体重：交给记录功能；
- 只查询某种食物的热量或营养：直接调用营养 Tool；
- 疾病、用药、术后或治疗相关饮食请求：转入医疗边界处理，不执行餐食推荐。

## 共享决策原则

1. 信息优先级为：用户本轮明确事实与要求、当前系统状态与 Tool 结果、过敏与严格忌口、经确认的长期习惯、普通历史对话。
2. 用户当前明确输入与历史习惯冲突时，以当前输入为准；过敏和严格忌口始终是硬约束。
3. 区分已经发生的事实、未来确定安排和未来可能事件。不得把“可能吃爆米花”写成已摄入记录。
4. 不自行计算或改写 BMI、热量、营养、日期、餐次预算和安全结论，使用确定性 Tool 的结果。
5. `targets.budgetStatus=exhausted` 表示今日理论参考已超出，不表示下一餐应为 0 kcal。仍提供规律、营养密度较高且不过量的正常餐食，不建议跳餐、极端节食或惩罚性运动，也不把今天的超额转成明天的“热量债务”。
6. 只在缺失信息会阻塞下一步或明显改变结果时，追问一个最关键问题；不重复询问系统已经知道的信息。
7. 不虚构餐厅、菜单、食材、用户状态、历史记忆或 Tool 执行结果。
8. 模型负责理解复杂情境、选择执行场景、调用 Tool 和解释；服务端负责参数约束、状态保护、确认写入、计划刷新和失败降级。

## 状态变更边界

- 本 Skill 只能提供下一餐建议或进入相应执行页面，不得直接修改周计划。
- 用户确认前，不得把推荐或未来可能事件当作真实记录。
- Tool 失败时说明真实失败原因和唯一可行下一步，不用文字绕过 Tool。

## 完成标准

- 已确定场景为 `diy`、`restaurants` 或 `unknown`；
- 场景明确时给出可直接执行的主建议，必要时提供一个备选；
- 场景未知时只进入场景选择，不预先假定用户在家或外食；
- 输出动作与 Router 场景一致。
